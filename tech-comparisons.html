ClimatePros Stream 2 — decision reference for technology choices

Knowledge Graph DB — Feedback Loop for Bid Extraction

Recommended: Neo4j CHOSEN vs Azure Cosmos DB Gremlin API ALTERNATIVE
Storing estimator correction feedback as a graph to improve future AI bid-sheet extractions. Neo4j wins on native LLM/LangChain integration, Cypher simplicity, and built-in graph analytics.
Factor Neo4j Cosmos DB Gremlin
Query language Cypher — intuitive, concise Gremlin — verbose, harder to read
LLM / RAG integration Native LangChain Neo4j connector, GraphRAG support No first-class LLM tooling
Pattern mining Graph Data Science library (built-in) Needs external tooling
Traversal performance Native graph storage (index-free adjacency) Graph layered over doc store — slower
POC ramp speed Aura free tier, up in minutes More Azure infra setup
Cost at POC scale Free tier covers 30–100 bids/week Always paid
Azure ecosystem fit Works via API Native Azure managed service

Real-time Communication — Bid Extraction & Notifications

Recommended: WebSocket CHOSEN vs API Polling ALTERNATIVE
Production system needs real-time extraction streaming, multi-role notifications (estimator → PMO reviewer → FieldGenix), and LLM field-by-field output. WebSocket covers all of this. API Polling does not.
Factor WebSocket API Polling
LLM streaming output Native — fields populate live Not possible
Multi-role notifications Server pushes to each role instantly Delayed by poll interval
FieldGenix push on approval Real-time trigger Delayed
Server load at scale Event-driven — pushes only when needed Repeated requests even when idle
Implementation complexity Medium — needs reconnect + heartbeat Simple
Corporate firewall risk Use wss:// on port 443 — mitigated No risk
Horizontal scaling Needs Redis Pub/Sub — solved Stateless, scales easily
Known issues & fixes
• Corporate firewall — use wss:// on port 443
• Idle timeout drops — 30s client heartbeat ping
• Reconnect on drop — exponential backoff on client
• Auth on reconnect — pass JWT token on WS handshake
• Multi-instance routing — Redis Pub/Sub as message broker
• Azure tier limits — Standard tier or Azure App Gateway
Discussed: 28 Jul 2026

Redis Cache Provider — WebSocket Pub/Sub Broker

Final Decision: Azure Cache for Redis CHOSEN
Stream 2 app is planned to be deployed on Azure. Azure Cache for Redis will sit in the same VNet — native, secure, zero cross-cloud overhead. AWS ElastiCache was considered (another team already has it) but ruled out due to the issues below.
Factor Azure Cache for Redis AWS ElastiCache (why we didn't use it)
App connectivity Native — same VNet as the app App is on Azure; ElastiCache is VPC-bound on AWS — no safe public endpoint
Cross-cloud access Not needed Requires AWS ↔ Azure VPN tunnel — not in place, significant infra work
Security TLS + VNet-private by default Cannot expose ElastiCache publicly safely — brute-forceable, no enforced TLS
Cost reality Small Redis instance, predictable "Free" shared instance — but VPN tunnel setup costs more than a new Redis
Ops ownership Fully owned by Stream 2 team Shared with another team — incident ownership unclear
If AWS ElastiCache was used — issues you'd face
• No public endpoint — ElastiCache is VPC-private; you can't reach it from Azure without a VPN tunnel
• VPN tunnel required — AWS Site-to-Site VPN + Azure VPN Gateway setup; doesn't currently exist in this stack
• Security risk if exposed — making Redis publicly accessible opens it to brute-force attacks
• Cross-cloud latency — adds network hop between Azure app and AWS Redis on every Pub/Sub event
• Shared ops risk — another team's workload or misconfiguration can affect Stream 2
