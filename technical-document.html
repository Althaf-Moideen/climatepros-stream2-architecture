01

Stream 2 Overview

ClimatePros is an AI-assisted estimating platform for commercial refrigeration bids. Estimators upload engineering drawing packages; the platform extracts a structured takeoff with a history-grounded AI pass, prices it deterministically, routes it through a review-and-approval workflow, and delivers the FieldJetX Excel (the only file sent to FieldJetX) plus an in-app summary PDF. It runs on Microsoft Azure, with Zeus operating on the client's on-premises Mac Studio ("Tundra") for spec analysis — so structured bid data never leaves the client's premises.

Design principle — Two-model AI extraction: Anthropic Claude Sonnet 4.6 extracts structured takeoff from engineering drawings (cloud, Anthropic API, no prompt logging). Zeus (Claude Sonnet 4.6, on-premises Mac Studio "Tundra") analyses specs and grounds extraction in the client's real FieldJetX bid history. Models never emit prices — every dollar is deterministic code.
Zeus design principle: Zeus is ClimatePros' own AI, running Claude Sonnet 4.6 on-premises on the client's Mac Studio "Tundra", wired to FieldJetX — so it analyses specs grounded in real prior bids (equipment names, N/E/R/X statuses, rates), raising accuracy on exactly the domain-specific fields a generic model guesses at. A Knowledge Graph tracks estimator corrections (BidItem → Correction → Equipment nodes, SIMILAR_TO edges) and promotes them to the golden set weekly, continuously improving extraction without retraining.

Data flow overview

Estimators submit drawings through FieldJetX Web App → FastAPI validates the FJX session token and RBAC, then enqueues an analyze job on Azure Service Bus → KEDA workers consume the queue, fanning out one Celery task per page → each page task calls Anthropic Claude Sonnet 4.6 (cloud, drawing extraction) via asyncio.gather(), which extracts structured takeoff data and passes it to Zeus (on-prem, spec analysis) → a Celery chord() fans all page results back in to the Reconciler → deterministic pricing engine prices the reconciled items → WebSocket / HTTP polling returns real-time status to the estimator → corrections feed the Knowledge Graph for continuous improvement → on approval, Excel is pushed to FieldJetX (the only outbound file).

Five key design rules

  1. Drawing images go to Anthropic API (cloud, no prompt logging) — only reconciled structured data reaches Zeus on-prem; raw drawings never traverse the on-prem boundary outward.
  2. Spec data stays on-prem (Zeus) — all spec analysis and FieldJetX bid grounding runs on the client's Mac Studio "Tundra"; structured bid data never leaves the client's premises.
  3. Models never emit prices — every dollar is deterministic code; no model call touches a price field.
  4. One cloud AI active: Anthropic Claude Sonnet 4.6 via Anthropic API — region-pinned, DPA-covered, no prompt logging.
  5. prompt_version stamped on every bid and ai_calls record — full traceability chain; dead-letter queue captures all failed jobs — nothing is silently lost.

05

Application Workflow

1 · Upload & Normalise — deterministic, no AI

Detect format → convert everything to PDF (DOC via LibreOffice, CAD via exporter, images wrapped) → render each page (200 DPI, auto-bumped to 300 DPI for dense schedule / E-size sheets) → obtain text by the most accurate route: native text extraction for born-digital PDFs (exact + free); scans, photos and image-only pages carry no text layer, so they are marked needs_vision and read directly by Anthropic Claude Sonnet 4.6 vision in Step 2 → quality gate flags blank/blurry/garbled pages instead of passing them silently. Uniform per-page images land in Blob + Azure SQL so all models see consistent inputs for every document type.

2 · Analyze — Anthropic extract + Zeus analyse

Anthropic Claude Sonnet 4.6 (cloud, Anthropic API, no prompt logging) receives page images and extracts the takeoff into a constrained JSON schema (validated + auto-retried), with every item linked back to its source page. Passes structured data (no raw drawings) to Zeus. Zeus (on-prem, Mac Studio "Tundra") performs spec analysis on the Anthropic-extracted data, guided by a domain prompt + dynamic few-shot examples from the Knowledge Graph and grounded in the client's prior FieldJetX bids (real equipment names, statuses, quantities). Workers fan out via Celery group() (one task per page); each page task calls Anthropic extractor and Zeus spec analyzer in parallel via asyncio.gather(). A Celery chord() fans all page results back in to the Reconciler. No prices here.

3 · Estimate — pure deterministic code

Deterministic engine maps each item to a rate line (no rate → unpriced flag, never $0), prices by status (N/E/R/X) in Decimal, and pins the rate-card version → honest + draft totals, fully re-runnable. Rate lines and formula inputs are drawn from the client's FieldJetX bid history via Zeus. No model call in this step.

4 · Review & Approval — human sign-off

Estimator submits; reviewer/manager approves or rejects with sign-off; audit-logged state machine. Open RFIs or unpriced items block final sign-off but not drafting. Approver ≠ estimator (separation of duty enforced).

5 · Deliver — Excel + PDF

Excel pushed to FieldJetX via direct API call (the only file that leaves the system); in-app summary PDF generated for viewing / download. FieldJetX must expose a REST ingest endpoint — API key stored in Key Vault (see OI-01).

06

Core Services

1 · Intake — get the drawings ready

Takes any file — PDF, Word, CAD, scan or photo — and turns it into clean, consistent pages. Word and CAD are first converted to PDF; each page is rendered as an image (200–300 DPI). It then gets the text the most accurate way: native text straight from normal (vector) PDFs, or Anthropic Claude Sonnet 4.6 vision for scans and photos (more accurate than OCR on messy drawings). Blurry or blank pages are flagged (needs_review) instead of guessed. No AI decisions here — just preparation.

2 · Analyze — Anthropic extracts (cloud), Zeus analyses (on-prem)

Anthropic Claude Sonnet 4.6 — running via Anthropic API (cloud, no prompt logging) — receives page images and extracts the takeoff (equipment, sizes, quantities and each item's status N/E/R/X) as structured data (JSON), with every item linked back to the page it came from. Drawing images are processed by Anthropic; only structured data is passed onward.

Zeus — the client's own AI, running Claude Sonnet 4.6 on the client's on-premises Mac Studio ("Tundra"), connected to FieldJetX — performs spec analysis on the Anthropic-extracted structured data. Before analysing, Zeus queries the Knowledge Graph for SIMILAR_TO correction edges as dynamic few-shot examples, plus prior bid details from FieldJetX as grounding context. Spec data stays fully on-prem throughout. Workers fan out via Celery group(); each page task calls Anthropic extractor and Zeus spec analyzer via asyncio.gather(); a Celery chord() fans results back in to the Reconciler.

Zeus grounding: Zeus queries the FieldJetX database to retrieve historical bid records for the same client (prior equipment lists, statuses, sizes, rate references) and queries the Knowledge Graph for correction-derived SIMILAR_TO edges as dynamic few-shot examples. Spec data stays fully on-prem throughout.

3 · Reconcile — merge into one list

Merges Anthropic's and Zeus's results into one clean list of bid_items. Matches the same item across both, then merges field by field: agreement raises confidence, a confident value fills a blank, and any disagreement or missed item becomes an RFI. Fully deterministic — the same input always gives the same result, and every decision is logged.

Built to scale: pages run in parallel on KEDA workers; drawing-hash-based Redis caching returns results at zero AI cost for repeat layouts (national chains with standard store templates).

4 · Estimate — work out the cost

Prices the job with plain code — no AI touches the dollars. Each item is matched to a rate card line — rates and formula parameters are populated from the client's FieldJetX bid history via Zeus. An item with no rate is flagged unpriced, never counted as $0. Produces two totals — an honest total (confirmed items) and a draft total (includes uncertain/RFI items) — using Decimal money (no rounding drift). The rate version is pinned to the bid, so a re-run always gives the same figure.

5 · Review & Approval — people sign off

The bid moves through clear states: draft → in_review → approved → finalised. The estimator submits; a reviewer or manager approves — the approver cannot be the estimator. Open RFIs or unpriced items block final sign-off but not drafting. Every step is kept in an immutable audit trail.

6 · Deliver — send the result

Once approved, the platform makes a direct API call to FieldJetX to push the generated Excel file — the only file that leaves the system. A summary PDF of the findings and bid details is also generated in-app for viewing or download.

FieldJetX API requirement: FieldJetX must expose a REST ingest endpoint that accepts the Excel via multipart/form-data. The API key is provisioned by FieldJetX and stored in Azure Key Vault. This endpoint must be in place and verified before the Deliver step can go live (see OI-01).

7 · Knowledge Graph — continuous accuracy improvement

Tracks every estimator correction as a graph: BidItem → Correction → Equipment nodes with SIMILAR_TO edges linking corrected items to canonical equipment records. Zeus queries these edges at spec-analysis time for dynamic few-shot examples that are far more relevant than static prompt examples. On a weekly promotion cycle, validated corrections are folded into the golden set, generating a new prompt_version. This creates a continuous accuracy-improvement loop without any model retraining — the more estimators correct, the better Zeus analyses.

Feedback loop: Estimator edits → item_edits table → Knowledge Graph nodes → weekly promotion review → golden-set update → new prompt_version stamped on all future bids. Every correction becomes compounding signal.

Applied-AI Engineering & Governance

Observability & audit trail

Every model call — Anthropic Claude Sonnet 4.6 (extractor) and Zeus (spec analyzer) — logs bid_id, model+version, prompt_version, tokens, latency, and cost to ai_calls + App Insights. Raw outputs are stored per run, forming the full traceability chain: bid → prompt_version + raw Anthropic extraction output + raw Zeus spec-analysis output → reconciled items → estimate → approver.

Evaluation — golden set + CI gate

A versioned golden set (refrigeration + HVAC split) scores recall, status accuracy, and size-match. Evals run in CI and gate every prompt or model change. The reconciler threshold (default 0.6) is tuned against this set.

Hard gate thresholds (CI pass/fail): extraction recall ≥ 95% · size-match ≥ 90% · status (N/E/R/X) accuracy ≥ 95% · no metric regresses more than 2 percentage points below the current production baseline for that prompt_version. A change that breaks any threshold is blocked from promotion.

Feedback loop & Knowledge Graph

Estimator corrections are captured in item_edits and written as BidItem → Correction → Equipment nodes with SIMILAR_TO edges. Zeus queries these edges at spec-analysis time as dynamic few-shot grounding. On a weekly promotion cycle, validated corrections are folded into the golden set, generating a new prompt_version — continuously improving analysis accuracy without model retraining.

Prompt versioning & rollout

Prompts (system + few-shot) live in the repo as versioned templates; a content hash produces the prompt_version stamped on every bids row and ai_calls record. Changes ship behind a feature flag, must clear the eval gate before promotion, and can be rolled back instantly by flipping the flag — no redeployment required.

Prompt-injection & adversarial-input defence

Native-text PDFs can carry adversarial instructions into the extraction prompt, so document text is treated as untrusted data, never instructions:

  1. Drawing content is passed in a clearly delimited data channel with system-prompt role-framing.
  2. Structured-output enforcement — the model must return the constrained bid_item schema, validated + auto-retried; free-form injected directives cannot alter control flow.
  3. The deterministic reconciler applies quantity/size bounds & sanity checks; anything implausible becomes an RFI.
  4. Models never emit prices — no injection can move a dollar figure.
  5. The FieldJetX bid history Zeus retrieves is treated as untrusted data too — supplied in the same delimited data channel, never as instructions.

Compliance & data governance

Anthropic Claude Sonnet 4.6 runs via Anthropic API (region-pinned to a supported EU/US region, no prompt logging, not used for training under the Anthropic API Data Processing Addendum). Drawing images are processed by Anthropic in the cloud; no raw drawings are stored beyond the processing window.

Zeus runs fully on-premises on the client's Mac Studio "Tundra" — spec data never leaves the client's premises. Only structured drawing data (no raw images) is passed from Anthropic extractor to Zeus spec analyzer. The FieldJetX bid history Zeus retrieves never leaves the trusted on-prem boundary.

Prompt/response content is redacted before external log sinks. GDPR/CCPA: client drawings processed under legitimate-interest/contract basis, retention-limited per §7, right-to-erasure honoured by the purge cascade. Models never emit prices.

Data boundary summary: Drawing images → Anthropic API (cloud, no logging, DPA-covered) → structured data only → Zeus (on-prem, Mac Studio "Tundra") → spec analysis output → Reconciler (cloud) → deterministic pricing. No raw drawings leave the extraction step.
